# Нагрузочное тестирование и профилирование

Создание и обработка заданий измеряются отдельно. `load-tests/create.js` измеряет пропускную способность аутентифицированного POST и по умолчанию пишет в очередь `load`, которую исполнители не обслуживают; это позволяет отдельно оценивать API и БД. `load-tests/processing.js` отправляет задания в очередь по умолчанию, опрашивает результат до успеха и измеряет сквозную задержку, включая создание и опросы. Ни один из этих результатов нельзя считать чистым замером выполнения обработчика.

```sh
docker run --rm --network job-platform_default -v "$PWD/load-tests:/scripts" \
  -e VUS=500 -e DURATION=30s grafana/k6:1.3.0 run /scripts/create.js
docker run --rm --network job-platform_default -v "$PWD/load-tests:/scripts" \
  -e VUS=16 -e JOBS=1000 -e SLEEP_MS=100 grafana/k6:1.3.0 run /scripts/processing.js
```

Переходите к обработке 10/50/100 тысяч заданий после проверки доступного хранилища, времени выполнения и загрузки исполнителей. Нагрузка создания намеренно увеличивает необслуживаемую очередь; остановите клиентов перед измерением её завершения. Для проверки обратного давления задайте `QUEUE=default`, `SLEEP_MS=100` и создавайте задания быстрее, чем исполнители их выполняют. Grafana покажет рост очереди, а число принятых каждым исполнителем заданий останется в пределах N+Q. БД хранит накапливающийся объём незавершённой работы без программного ограничения, тогда как память исполнителя и число его активных назначений ограничены.

Фиксируйте процессор и память машины, ограничения виртуальной машины Docker, версии Go и среды выполнения, интервал опроса, N/Q исполнителя, длительность обработчика, выборку трасс, число заданий, пропускную способность и p95 ожидания от готовности до выдачи. Опрос задаёт нижнюю границу задержки. Сравнивайте 1/2/4/8 исполнителей с одинаковым параллелизмом на процесс; не меняйте интервал опроса и размер очереди между строками сравнения. Реальные локальные запуски и область измерений описаны в [отчёте о производительности](performance-results.md).

```sh
go test -run='^$' -bench=. -benchmem ./internal/...
```

Микротесты измеряют передачу заданий пулу через канал, сериализацию protobuf-назначений, расчёт задержки повтора и работу реестра обработчиков с декодированием JSON. Они не включают затраты БД или сети.

pprof по умолчанию выключен. Запустите локальный процесс с `PPROF_ADDR=127.0.0.1:6060` и исключите доступ из публичных сетей. Процессу также нужны обычные переменные окружения выбранной роли.

```sh
go tool pprof 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'
go tool pprof 'http://127.0.0.1:6060/debug/pprof/heap'
go tool pprof 'http://127.0.0.1:6060/debug/pprof/goroutine'
```

Профилировать внутреннюю работу микротеста исполнителя можно командой `go test -run='^$' -bench=BenchmarkWorkerPool -cpuprofile=cpu.prof -memprofile=heap.prof ./internal/worker`. Анализируйте профили на фиксированной нагрузке. Перед оптимизацией подтверждайте предполагаемые узкие места замерами задержек и БД.
