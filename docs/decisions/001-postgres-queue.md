# ADR-001: PostgreSQL как надёжное хранилище очереди

Статус: принято.

Проблема: задание должно переживать гибель процесса, конкурирующие планировщики не должны назначать одну активную попытку одновременно, а записи состояния и истории должны быть согласованы.

Варианты: канал в памяти прост, но не переживает сбои и не координирует независимые процессы. Брокер вместе с PostgreSQL масштабирует выдачу, но усложняет двойную запись и подтверждения. Один PostgreSQL обеспечивает надёжное транзакционное получение с блокировкой строк.

Решение: PostgreSQL с короткими транзакциями SKIP LOCKED, токенами аренды и историей попыток. Выбор лидера не требуется. Каналы ограничивают только локальное выполнение. Отдельные исполняемые файлы API, планировщика и исполнителя явно разделяют развёртывание и области отказа.

Последствия: важны пропускная способность записи БД и vacuum; опрос добавляет задержку. Следующий этап с брокером должен сохранить надёжное владение и защиту токенами и использовать outbox вместо несогласованной двойной записи.
