# Устройство базы данных

`jobs` хранит текущее состояние жизненного цикла. `job_attempts` хранит неизменяемую идентичность назначения и его итог. `workers` хранит идентификаторы исполнителей, подписки на очереди, допустимую загрузку и время heartbeat. Токен попытки уникален; после ручного сброса лимита попыток исторические записи сохраняют отдельные идентификаторы. Внешние ключи предотвращают появление истории без задания. Ограничение CHECK требует токен и срок аренды для RUNNING и их отсутствие для остальных состояний.

Создание использует `INSERT ... ON CONFLICT(queue,idempotency_key) DO NOTHING RETURNING ...`. Если конкурирующая вставка выиграла, выполняется отдельный запрос с уровнем изоляции READ COMMITTED. Уникальное ограничение разрешает гонку создателей; следующий запрос видит уже зафиксированного победителя. Пустые ключи представлены NULL и не конфликтуют.

Получение задания блокирует строку исполнителя, подсчитывает его активные назначения, затем блокирует подходящие строки заданий:

```sql
SELECT id FROM jobs
WHERE status='READY' AND queue=ANY($1)
ORDER BY priority DESC, created_at, id
LIMIT $2 FOR UPDATE SKIP LOCKED;
```

В той же транзакции устанавливается RUNNING, увеличивается число попыток, назначается токен и создаётся запись истории. Блокировки удерживаются до фиксации; gRPC-ответ отправляется после неё. Потеря ответа может оставить аренду задания, неизвестного исполнителю; истечение срока безопасно возвращает его в обработку.

Частичные индексы обслуживают выдачу READY по приоритету и FIFO, подготовку отложенных заданий и истёкшие аренды. Индекс по времени создания и UUID поддерживает курсорную пагинацию. Индексы времени heartbeat и attempts(job_id,id) используются для проверок состояния и аудита. Фильтрация по статусу, типу или исполнителю может читать больше строк: измеряйте реальные распределения перед добавлением всех возможных составных индексов. Фиксированные приоритеты могут приводить к бесконечному ожиданию низкоприоритетных заданий.

Используйте явные версионированные миграции up/down через golang-migrate: приложение не создаёт и не меняет схему при запуске. Минимальный и максимальный размеры пула, срок жизни соединений и предел простоя задаются явно. Планируйте число соединений как сумму подключений экземпляров API и планировщика; исполнителям подключения к БД не нужны. Следите за частыми изменениями строк, мёртвыми версиями строк, autovacuum, диском и задержкой репликации. Для долгоживущей истории потребуется политика хранения и архивирования.

Воспроизвести план запроса можно командой:

```sh
docker compose exec -T postgres psql -U jobs -d jobs -c "EXPLAIN (ANALYZE, BUFFERS) SELECT id FROM jobs WHERE status='READY' AND queue='default' ORDER BY priority DESC,created_at,id LIMIT 100 FOR UPDATE SKIP LOCKED"
```

Измеренный план пустой очереди находится в [database-explain.txt](database-explain.txt), а получение 100 строк из заполненной очереди `load` — в [database-explain-load.txt](database-explain-load.txt). Это результаты для зафиксированных локальных наборов данных, а не общая гарантия производительности. EXPLAIN ANALYZE выполняет запрос и ненадолго получает блокировки, поэтому проводите контролируемые эксперименты на демонстрационной БД.
