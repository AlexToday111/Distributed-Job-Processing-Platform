# Архитектура

API сохраняет задания в надёжном хранилище и предоставляет запросы к заданиям и попыткам. RPC-обработчики планировщика по запросу получают задания и фиксируют назначения; цикл обслуживания переводит готовые по времени задания в очередь выполнения и восстанавливает истёкшие аренды. Исполнители запрашивают задания только при наличии свободных мест. Ни один компонент не использует канал в памяти как распределённый источник истины.

API аутентифицирует Bearer-токены, проверяет тела запросов размером не более 1 МиБ, передаёт метаданные корреляции и преобразует ошибки домена и хранилища в единый формат. Транзакции PostgreSQL обеспечивают согласованные переходы состояний. Правила сосредоточены в `domain.CanTransition`; SQL реализует только эти переходы. Проверки готовности API и планировщика проверяют подключение к БД, а исполнителей — недавнее успешное RPC-взаимодействие.

Для первой версии выбран unary RPC вместо серверного или двунаправленного потока. Запрос заданий исполнителем напрямую выражает ограничение нагрузки, все вызовы имеют предельное время выполнения, а повторное подключение не требует локального реестра сессий планировщика. Цена решения — дополнительные опросы и RPC-вызовы, а также задержка отмены до одного интервала heartbeat. В дальнейшем потоковый протокол может сократить задержки, сохранив семантику надёжного хранения.

Обслуживание очереди не требует лидера. Задания с наступившим временем запуска и истёкшие аренды обрабатываются ограниченными пакетами с SKIP LOCKED. Строка исполнителя блокируется только при получении заданий, чтобы ограничения его загрузки соблюдались между планировщиками. Heartbeat и подтверждение результата проверяют токены владения. Каждый процесс должен иметь отдельный идентификатор исполнителя: случайное повторное использование идентификатора объединяет их загрузку и идентичность. Общий токен исполнителей подтверждает принадлежность кластеру, но не обеспечивает индивидуальную авторизацию каждого исполнителя.

Масштабирование добавляет процессы исполнителей и экземпляры планировщика. Число операций записи PostgreSQL, частые изменения строк и обслуживание БД ограничивают рост. Наблюдайте за восстановлением аренды, задержкой выдачи, autovacuum, ростом очереди и использованием соединений. PostgreSQL делает границы транзакций явными; брокер становится полезен, когда нагрузка выдачи и записи превышает возможности БД. Переход должен сохранять доставку как минимум один раз и защиту от устаревших исполнителей.

## Этапы реализации

| Этап | Цель и изменяемые файлы | Изменения хранилища и API | Риски параллелизма и критерии приёмки |
|---|---|---|---|
| 0 Подготовка | cmd, config, логирование, Compose, CI | явная миграция; проверки состояния | ограниченное время запуска и завершения; сборка и готовность |
| 1 API заданий | domain, API, repository | задания; создание, чтение, список, идемпотентность | дублирование создания; гонка 100 запросов с одним ключом |
| 2 Исполнитель | реестр, выполнение, тесты | обработчики JSON | N горутин, Q элементов канала; тесты тайм-аутов и завершения |
| 3 Планировщик | транзакционная выдача и подготовка | условия готовности и аренды | конкурентная выдача; отсутствие дублирующихся аренд |
| 4 gRPC | proto, service, клиент исполнителя | register/heartbeat/claim/complete | предельное время вызовов, проверка загрузки в БД |
| 5 Надёжность | переходы repository и восстановление | попытки, повторы, DLQ, отмена и возврат в очередь | защита токенами; истёкшую аренду нельзя продлить |
| 6 Наблюдаемость | метрики, трассы, панель | корреляция и метаданные трассировки | ограниченное число меток; трассы асинхронного выполнения |
| 7 Укрепление | runtime и безопасный HTTP-обработчик | аутентификация, лимиты, готовность | корректное завершение, защита от SSRF |
| 8 Тестирование | модульные тесты, Testcontainers, CI | изолированные тестовые БД | гонки, блокировки, восстановление, повтор подтверждения |
| 9 Производительность | микротесты, k6, pprof | без изменений схемы | фиксация реального окружения и результатов |
| 10 Документация | README, OpenAPI, ADR, демонстрации | описание контрактов | воспроизводимые проверки отказов и производительности |

После этапов выполняются форматирование, vet, тесты, детектор гонок, запуск Docker и проверка документации. Подтверждения записываются в отчёт о производительности без вымышленных заявлений о возможностях промышленной эксплуатации.
